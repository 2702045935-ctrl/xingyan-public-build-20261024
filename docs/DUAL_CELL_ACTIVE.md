# 双 Cell 双活底座

结论日期：2026-11-17

这套方案用于把 `43.242.194.89` 和 `192.140.179.176` 接成统一的双 Cell 底座，
但当前只允许以休眠方式验证，不能直接切线上流量。

## 统一拓扑

- 逻辑分片固定为 7 片，不把 43 的旧 6 片和 192 的 7 片硬拼。
- Cell A 基线 owner 为 `0..3`。
- Cell B 基线 owner 为 `4..6`。
- 两台机器都保留 7 片完整副本，负责读取本地副本和故障接管。
- 每个对象同一时刻只能有一个 lease owner。
- 所有跨片用户查询先查冻结用户目录，再请求唯一 owner。

## 写入规则

普通社交数据采用 `owner-durable-outbox`：

1. 只允许 lease owner 写入。
2. owner 完成本地持久化后返回成功。
3. outbox 幂等复制到另一台机器。
4. 复制游标只在副本持久化后前进。

支付、账本、余额等关键实体采用 `peer-durable-outbox`：

1. owner 本地落盘后不能立即宣告提交。
2. 必须等对端副本持久化确认。
3. 对端不可用时拒绝关键写入，不降级成单副本真钱提交。

两台机器无法同时做到零数据丢失和任一时刻都接受关键写入。这里明确选择资金安全：
单机故障窗口内，关键写入宁可短暂不可用，也不允许双主或单副本提交。

## 切主规则

1. lease 由外部一致性存储决定，生产环境不能把共享目录当作 lease 中心。
2. 新 owner 必须等旧 lease 过期并取得更大的 epoch。
3. 新 owner 只能从已确认的副本事实继续写。
4. 旧 owner 恢复后只能作为副本追平，未取得新 lease 前写入必须被 fencing 拒绝。
5. 接管前必须检查复制延迟；超出允许窗口时不得自动切主。
6. 支付权威固定唯一分片，不能随社交哈希漂移。

## 当前验证

契约检查：

```text
node server/tools/dual-cell-active-plan.js \
  --plan=docs/DUAL_CELL_ACTIVE_PLAN.template.json \
  --out=<契约报告>
```

离线故障演练：

```text
node server/tools/dual-cell-failover-drill.js \
  --out=<演练报告>
```

演练覆盖：

- 43/192 owner 集合互斥且完整覆盖 7 片。
- 非 owner 写入被拒绝。
- 跨机幂等复制，不重复事件。
- 支付关键事件复制后才能视为已提交。
- 旧 lease 过期后 epoch 递增。
- 旧 owner 恢复后写入被 fencing 拒绝。
- 故障接管和故障回切后两台机器事件集合一致。

## 上线门槛

以下条件全部满足前，计划中的 `activation.writesEnabled` 必须保持 `false`：

1. 生产 lease 接入真正的一致性服务，并有超时、续租、失联和时钟漂移告警。
2. 43/192 的故障域、网络路径、带宽和磁盘延迟完成实测。
3. 两台机器各自 7 片完整副本完成数量、序列、哈希和时间对账。
4. 所有用户、好友、群、朋友圈、支付写路径都接入唯一 owner 网关。
5. 断网、丢包、进程暂停、磁盘满、复制积压和双主脑裂演练通过。
6. 关键写链路有明确降级页、审计记录和人工恢复步骤。
7. 公网网关只按 owner 分流，不允许浏览器直接选择任意 Cell 写入。
8. 可一键回滚到单 Cell 稳定版本，并保留可验证的数据恢复点。

离线演练通过只证明所有权和复制机制成立，不等于可以接生产流量。
