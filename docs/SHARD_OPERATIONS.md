# 分片管控规则

## 当前生产映射

- 公网入口：`43.242.194.89:5443`
- 公网入口配置：7 片，SSH 隧道端口 `15299-15899`，步长 100
- 业务落点：`192.140.179.176`，后端端口 `7080-7680`，步长 100
- 业务服务：`xingyan-mainline-shard@0-6`
- 程序目录：`/opt/xingyan-mainline/app`
- 启动脚本：`/opt/xingyan-mainline/run-shard.sh`
- 数据目录：`/opt/xingyan-mainline/data`
- 拓扑名称：`server-b-shards-7`
- 43 本机还有独立的 `chris-shard@0-5` 服务组，不得与上面的 mainline 七片混为一组操作。

任何操作都必须同时写明逻辑分片 ID、服务名、入口隧道端口、后端端口和目标机器。

## 唯一分片清单

机器可读清单：`server/shard-runtime-production.json`。

每个分片必须登记以下字段：

| 字段 | 含义 |
| --- | --- |
| `logicalId` | 永久逻辑分片编号 |
| `service` | systemd 服务名 |
| `host` | 实际承载机器 |
| `backendPort` | 业务进程监听端口 |
| `entryPort` | 前置隧道或代理端口 |
| `dataDir` | 唯一数据目录 |
| `topologyId` | 路由计划所属拓扑 |
| `role` | `chat`、`call-signal` 或明确的服务角色 |
| `codeHash` | 当前部署代码哈希 |
| `health` | 最后确认时间和结果 |

清单缺失、重复、端口冲突、拓扑不一致或数据目录不唯一时，禁止部署。

## 变更流程

1. 只读盘点目标分片，确认服务、PID、端口、数据目录和代码哈希。
2. 生成最小补丁，不整文件覆盖线上源码。
3. 在隔离环境运行启动依赖检查、语法检查和自动回归。
4. 备份线上目标文件，记录备份绝对路径。
5. 普通聊天代码可先选一个分片做 canary，健康检查失败立即自动回滚。
6. 通过后按编号逐片滚动，每片完成健康检查才进入下一片。
7. 全部完成后验证公网健康、消息、通话、删除和保存。

通话归属属于协议变更，不能只 canary 一个分片。采用两阶段发布：

1. 先部署默认关闭的休眠代码，所有分片行为保持旧版。
2. 七片代码哈希一致后，确认 `activeCalls=0`、`ringingCalls=0`。
3. 通过共享功能开关一次性启用统一通话所有者。
4. 若任一健康、接通或音频检查失败，关闭开关并恢复旧行为。

## 通话分片约束

- 一通电话只能有一个权威状态所有者。
- 所有 `invite`、`accept`、`audio`、`hangup`、`timeout` 都进入该所有者。
- 目标用户分片由固定路由表计算，不允许按帧随机选择。
- 正常路径只发目标分片；广播只允许作为 presence 未知时的短暂兜底，并必须记录比例。
- 通话分片和其他聊天分片不得各自写一份可变的通话状态。
- 重连、重复接听和迟到帧必须幂等，不能改变已结束的通话。

## 发布硬门槛

- 启动依赖检查通过。
- `node --check` 通过。
- 分片拓扑、路由计划、数据清单测试通过。
- 单通话和跨片通话测试通过。
- 并发、断线重连、忙线、重复接听和挂断测试通过。
- canary 分片健康失败时自动回滚。
- 操作日志必须包含操作前后 PID、端口、哈希和健康响应。
