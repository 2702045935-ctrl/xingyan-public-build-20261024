# 亿级分片底座就绪评估

结论日期：2026-11-17

## 结论

当前版本不能直接作为“亿级并发分片底座”接入线上。

当前可以进入的是“7 分片候选休眠部署和受控逐片发布”，不是“物理分片已经完成”，
更不是“亿级用户/并发已经就绪”。

不允许因为路由、owner 和发布控制测试通过，就把共享数据目录直接当成物理分片。

## 亿级硬门槛

以下条件全部满足前，不得标记为亿级底座：

1. `user-shard`、`chat-shard`、`moment-shard`、`payment-authority` 和
   `object-store` 使用真实隔离的权威存储，不再共享可变目录。
2. 所有写路径都按对象固定 owner，并由 fencing token 防止旧 owner 复活。
3. 消息、会话摘要、投递、已读和事件发布具备单事务或可证明的 outbox 一致性。
4. 超大群具备独立分区、限流和热点迁移能力，不会压垮单一 chat shard。
5. 图片、视频和文件进入对象存储，具备分片上传、去重、转码队列和 CDN。
6. 至少跨多台计算节点部署，具备自动扩缩容、熔断、限流和容量水位保护。
7. 每个分片有独立指标、日志、追踪、慢查询和错误预算。
8. 完成单节点、单机房、消息总线、数据库和对象存储故障演练。
9. 支付事实与社交数据隔离，具备独立对账、回放、冻结和人工审计链路。
10. 在任何迁移前完成全量只读副本、数量/序列/哈希/时间对账，并保留可恢复回滚点。

## 现在可以做什么

1. 在维护窗口恢复 SSH。
2. 只读核对正式计划文件和 7 片运行状态。
3. 将分片底座候选以休眠模式逐片加载，`SHARD_ROUTE_PLAN_ENFORCED=0`。
4. 7 片全部健康、版本和计划哈希一致后，再讨论是否激活聊天 owner。
5. 数据迁移、物理分片、支付迁移和媒体迁移继续保持关闭。

## 物理目录契约

物理分片候选必须通过：

```text
node server/tools/shard-physical-layout-audit.js \
  --root=<物理候选根目录> \
  --route-plan=<冻结计划文件> \
  --out=<审计报告>
```

验收器要求每个分片只包含自己的 `users/friendships/chats/reads/friendmeta/
moments/moment-notices/messages`，拒绝共享根目录中的权威文件、重复 owner、
消息线程错片、符号链接和混入聊天分片的媒体对象。

## 接下来不能做什么

- 不能直接把候选 `server.js` 整文件覆盖线上稳定版本，因为稳定版与当前分支之间
  还包含通话等暂停中的改动。
- 不能把共享目录直接拆成 7 份后无对账上线。
- 不能以“路由测试通过”代替数据库、对象存储、网络和容量验证。
- 不能在没有维护界面和执行器回执的情况下批量重启 7 片。
